# Campura One · 可选视觉分析插件

**v0.2 / 2026-10-20：从头重做的等候时间试算原型。** 商户自行选择下载、安装和启用，独立目录、独立 Git 仓库。正式产品目标是 Windows 与 macOS。当前交付是需要 Python 的源码试算器，尚未提供普通商户可直接安装的签名安装包。

当前实现：纯计算模块、八个模拟场景、本机界面、订单去重与并行排程、餐饮到店/预订及零售到店区间、匿名时长样本的分位数更新、缺失/过期降级。没有训练模型、模型权重或云端请求；模拟的是未来适配器提供的结构化数据。**本版没有摄像头采集、视频预览、实际视觉识别，也没有真实订单、页面浏览或地图接口。**

原 v0.1 的合成视频与简易计数代码已从当前工作树移除，保留 Git 历史用于恢复。清理前整个仓库约 504 KB，未发现训练权重/检查点；不能把此次清理描述为释放了大型训练模型。商家 Flutter、学生端、PHP 和生产环境未改动。

## 1. 先运行

需要 Python 3.9+；运行仅使用标准库，不下载依赖、模型或视频。在本仓库目录执行：

macOS：

```sh
python3 run.py
```

Windows PowerShell（待 Windows 实机验证）：

```powershell
py -3 run.py
```

默认打开浏览器；也可用 `python3 run.py serve`（Windows 将 `python3` 换成 `py -3`）只启动服务，再打开终端给出的完整地址。`Ctrl+C` 停止。地址含本次进程的短期令牌，只监听 `127.0.0.1`。刷新页面会清除页面内存中的令牌，请从终端地址重新打开。

界面左侧选择场景、修改制作能力和地图路程，右侧分别显示当前人数与三类时间。默认服务时长浮动 ±20%，**这是可改的工程情景假设**。将浮动设为 0，可复现固定时长例题。高级 JSON 可以改已接订单、预订单状态、未来到达率、覆盖区域和匿名样本。

模拟快照也有有效期，界面每 10 秒重新检查，过期后隐藏相关总 ETA。“刷新模拟快照时间”明确模拟一次新观测，保留示例数值；不是重连摄像头。相邻数据的生成时间应尽量一致。截止本版，TTL 内的快照按当前状态近似计算，**不会把重复显示同一份快照当作服务进度事件，也不是逐秒倒计时**。有效期本身不构成准确性保证。

命令行也可试算：

```sh
python3 run.py example dining > /tmp/campura-demo.json
python3 run.py estimate /tmp/campura-demo.json
```

Windows 可用 `py -3 run.py example dining | py -3 run.py estimate -`。纯计算入口：`campura_vision.estimator.estimate(data, now=带时区的datetime)`，可注入时钟做可重复测试。

## 2. 产品口径

| 场景 | 起点 → 终点 | 第一版显示 |
| --- | --- | --- |
| 餐饮现在到店 | 进店 → 排队点单 → 可取餐 | 到店后等待范围 |
| 餐饮按路线到店 | 地图预计到店时刻 → 排队点单 → 可取餐 | 路程单列，只用来预测未来店况 |
| 餐饮预订 | 原线上下单时刻 → 可取餐 | 未确认显示“待确认”；确认后保留原起点，同时显示剩余时间 |
| 自选零售到店 | 进店 → 挑选 → 排队结账完成 | 总范围、分段和拥挤程度 |
| 自选零售预订 | — | 本版不提供 |

“当前排队人数”始终独立展示，不叫预计等候时间。店内总人数可能包含逛店、陪同、候餐的人；不能把它直接与已接单数相加。一个人不必然产生一单，多人也可能合一单。

因此模拟接口另有 `service_queue`：**尚未成为已接订单的点单交易，或尚未结账的零售交易**，包含等待交易数和服务中交易的剩余时间。它与原始 `queue_people` 分开。没有交易单位/进度依据，就保留人数与其他可算分段，停止总 ETA。后续可由人工计数、已校准的分组估计或服务事件提供；当前不声称相机已经能分组。

## 3. 计算方法

专业上，这是“需求预测 + 多服务台排队/排程 + 场景分析”。画面计数、转化率校准和订单制作排程是不同环节。本版计算可解释的有限情景，不使用黑箱模型直接猜分钟数。

### 3.1 已确认订单与并行制作

令：

- `B`：已接且未完成的订单数，线上/线下统一按稳定订单 ID 去重。
- `d`：每一单的制作时长，单位分钟，商家填写。
- `c`：同时可制作的订单数，即并行工位数。
- `v`：时长浮动比例；情景服务时长为 `d × (1−v)` 或 `d × (1+v)`。

全部积压订单都尚未开始、各单相同、没有插队时，新确认一单的简化检查公式：

```text
W = ceil((B + 1) / c) × d
B = 7 + 9 = 16，d = 1.5，c = 2
W = ceil(17 / 2) × 1.5 = 13.5 分钟
```

这不是“16 单都必须串行做完”。默认 ±20% 时，同一例题的制作情景范围为 10.8–16.2 分钟；到店还可能有点单过程，因此不能把这个数直接当到店总时间。

实际代码用最早空闲工位堆：

```text
已有制作中订单：每个占一个工位，以 remaining_minutes 表示剩余工作
空闲工位：可用时刻为 0
按 accepted_at、订单 ID 稳定排序排入已确认等待订单
对订单 i，选择最早空闲的工位 k：
  start_i  = max(arrival_i, available_k)
  finish_i = start_i + duration_i
  available_k = finish_i
```

事件是插件自有的**模拟状态快照协议**，不是现有 PHP 字段：同 ID 取 `updated_at` 最新记录；同时间相互冲突的状态会阻断订单 ETA。`pending` 未进入制作积压；`ready`/`cancelled` 不计积压；`preparing` 必须有剩余时长且数量不能超过工位数。线上线下重复的同一 ID 只计一次；若外部系统给同一笔交易两个 ID，必须由未来适配器先建立统一 ID，本模块无法凭人数识别重复订单。

实际指定的已确认预订单不再额外插入一单，使用其原队列位置：

```text
预订剩余等待 = 该订单预计可取时刻 − 当前时刻
预订总等待   = 已经过去的下单时间 + 剩余等待
```

未传 `preorder_order_id` 时展示“现在预订并立即确认（试算）”；这不表示真实订单已接单。确认时间不确定的真实 pending 订单没有 ETA。已完成订单仅在提供 `ready_at` 时显示实际总耗时。

### 3.2 未来到店、路上的新订单与点单队伍

`A` 为地图路程分钟数；`A=0` 是现在到店。未来需求输入分开：

- `online_orders_per_minute`：未来新增、直接确认的线上订单。
- `walk_in_orders_per_minute`：未来进入点单队伍的交易，**未包含在已接订单内**。

每个都有 `[低, 高]` 两个情景。当前它们全是明确填写的模拟值，没有“页面浏览 10 人 = 1 单”之类编造的系数。未来可用已确认订单的完整时间窗记录估计线上到达率，用本店匿名客流与成交的配对统计估计到店转化；浏览人数只在取得本店校准记录后加入。当前不实现该回归模型。

在一个情景内以间隔 `1/λ` 生成交易：第一笔在 `1/λ` 分钟；`λ=0` 表示此情景没有新增。**这是确定性的情景输入，不是泊松采样、概率保证或突发拥挤上界。**

1. 从当前待点单交易/服务进度出发，按点单工位排程。
2. 路程中在 `A` 之前加入的交易先排队，目标顾客在 `A` 入队。
3. 这些点单交易在点单结束后才成为厨房订单，避免与已确认积压重复。
4. 目标点单结束时刻记为 `T`；把 `T` 之前确认的线上订单及更早点单完成的到店交易加入厨房模拟。
5. 目标订单插入后，后来的订单不让它变慢，遵守先确认先制作。

```text
W_arrival(A) = ready_target − A
            = (T − A) + (ready_target − T)
```

路程 `A` 不加入显示的等待。例：16 单积压、两工位、1.5 分钟/单、无新订单、无点单队伍、点单 0.5 分钟，30 分钟后到达时原积压已做完，到店后等待是 2 分钟，而非 32 分钟。

同时刻到达的其他交易在目标前处理；订单 `accepted_at` 相同用 ID 排序。所有情景采用相同的这一规则。点单结束超过 120 分钟时停止总预测，提示超出窗口。

### 3.3 自选零售：挑选后再看收银队伍

`S` 为挑选时长，`A+S` 是顾客进入收银队伍的预计时刻。当前队伍与未来收银到达交易按收银工位排程：

```text
W_retail(A) = S + checkout_wait_and_service(A + S)
            = checkout_finish_target − A
```

不能把当前队伍完整地加在 `S` 后面：挑选期间队伍可能已经消退，也可能有新顾客先结账。`checkout_arrivals_per_minute` 是其他顾客未来加入收银队伍的交易率，包含已在店内购物的人；**不能再把店内总人数加一遍**。

当前工程初值为 **1–6 分钟**，明确“未按本店校准”。[深圳零售建筑实地研究](https://www.sciencedirect.com/science/article/abs/pii/S0360132321002432)研究的是在店总时长，不能证明纯挑选时长是 1–6 分钟；这里只把它作为待验证的宽初值，不声称代表所有校园小店。

匿名样本更新：

- 输入只接收 `{ minutes, space_occupancy_ratio }`，不需要人脸、顾客 ID 或轨迹。
- 将空间占用比例 `<0.25`、`0.25–<0.60`、`≥0.60` 分为三档；这些是工程展示阈值，非消防容量/拥挤安全判断。
- 只匹配当前拥挤档，最多 500 个样本；样本快照有效期 7 天。调用方负责构造该时间窗数据，本版不持久化样本。
- 匹配样本少于 30：仍用 1–6 分钟。30 个及以上：取线性插值的 P10–P90 范围。
- 本版这些样本也是模拟的，界面不会把它们写成实店验证。P10–P90 是样本描述，不是新顾客等待时间的 80%/90%保证。
- 拥挤仅用于选择同条件样本；没有证据时不乘任意“拥挤系数”。30 样本/7 天/阈值都需后续实店评估。

样本未来可来自经授权、短时匿名的“进入购物区域 → 加入收银区域”，完成后只保留耗时与拥挤档，删除会话内跟踪 ID；不能从任意一张静态图推得这个耗时。

入口、购物区、收银区任一区域不可见，或画面用途未确认：不输出零售总时间。可见收银区且有交易依据时仍可显示条件性的结账分段；挑选工程初值始终标为假设，不伪装成观察结果。

### 3.4 区间如何产生，何时失效

餐饮枚举制作时长系数、点单时长系数、线上到达率、到店到达率的端点组合。零售枚举挑选时长端点、收银时长系数、收银到达率端点。对各情景结果取最小/最大值，向外取整至 0.1 分钟。子区间极值可能来自不同情景，**不能简单相加子区间端点来重建总区间**。

这是有限情景包络，未证明覆盖全部中间参数，也未包含突发大单、不同菜品、批次烹饪、缺货、插单、人员变化、弃队等影响。正式店铺展示精度应在真实误差评估后决定；当前小数用于可检查的试算，不表示预测精确到秒。

| 数据 | TTL | 缺失/过期时 |
| --- | --- | --- |
| 视觉汇总、交易队伍 | 30 秒 | 人数标过期；相关到店总 ETA 停止 |
| 订单快照 | 60 秒 | 停止餐饮制作/预订总 ETA；点单段可保留 |
| 未来需求情景 | 60 秒 | 不假设未来需求为零；停止依赖它的总 ETA |
| 聚合页面浏览人数 | 60 秒 | 标过期；当前版本从不用于数值转化 |
| 匿名挑选样本 | 7 天 | 回到明确未校准的工程初值 |
| 地图时间 | 本次输入的 0–120 分钟 | 没有时仅保留“现在到店”；未来接入需另加路线数据有效期 |

时间要求带时区 ISO 8601；未来超过 5 秒的观测提示时钟问题。拒绝 NaN、无穷值、负数、非整数工位、逆序范围等非法输入。已接订单快照必须 `complete=true`，并含全部未完成订单；不能把不完整的接口分页当作完整积压。

## 4. 输入、输出与本机接口

自有输入模式：`schema_version=1, mode=simulation, kind=dining|retail`。完整样例由 `run.py example` 生成，字段与实现见 [samples.py](src/campura_vision/samples.py) / [estimator.py](src/campura_vision/estimator.py)。当前没有接管或新增现有业务 API 合同。

| 输入 | 内容与来源 |
| --- | --- |
| `capacity` | 每单制作时长/并行工位、每次点单或结账时长/工位、情景浮动比例 |
| `orders` | 完整模拟订单状态事件：ID、渠道标签、下单/确认/更新时间、状态、制作剩余时间 |
| `vision` | 模拟画面用途、覆盖区域、人数、可用地面占用比例；未知字段不授予能力 |
| `service_queue` | 模拟待办交易数、不含等待者的当前服务剩余时长数组、ordering/checkout、transactions 单位 |
| `forecast` | 模拟未来到达率范围；线上订单/到店点单/零售收银分别定义，不能重复计入 |
| `page_views` | 模拟的近期聚合活跃浏览人数；只展示，无身份数据 |
| `arrival_minutes` | 模拟地图预计路程；不读取学生定位 |
| `calibration` | 有限匿名耗时样本；当前仅内存计算 |
| `preorder_order_id` | 可选：定位某个已存在的模拟预订单；不填则是假设立即确认的新单 |

输出包括：三种结果卡片、范围、分段、状态、缺失原因、依据、计算时刻、各数据源更新时间、独立人数统计、拥挤程度。无效总 ETA 为 JSON `null`，不是零分钟。

本机开发接口：

- `GET /api/health`：版本、模拟模式、云未启用。
- `GET /api/examples` 与 `GET /api/example?name=dining`：模拟预设。
- `POST /api/estimate`：仅接收上述 JSON，最大 512000 字节。
- 所有 `/api/` 请求必须带 `X-Campura-Token`；仅接受自身 Host/Origin，无跨域授权；不记录请求日志、不持久化输入。

这些是独立原型接口，**尚不是商家端发现/集成协议**。令牌随进程结束失效，URL fragment 加载后从地址栏移除。其他本机高权限进程不在此轻量防护的隔离承诺内。

## 5. 架构与跨平台路线

选择“独立程序 + 同进程本地服务”。当前系统浏览器充当配置/试算界面；未来再打包桌面启动器/托盘与本地服务。主商家端不安装插件也能工作；插件单独下载升级，不写入 Flutter 工程。详见 [架构与输入适配计划](docs/ARCHITECTURE.md)。

云路线仍有采集成本：USB 或需要逐帧上传的 RTSP 源通常仍需本机采集、抽帧/解码。云只转移推理负担，不能保证本机完全不解码。后续优先评测摄像头低分辨率子码流、硬件解码和边缘网关，再确定最低电脑配置；不能将当前的纯计算耗时当作视频处理性能。

| 项目 | Windows 计划 | macOS 计划 | 当前状态 |
| --- | --- | --- | --- |
| 安装 | 独立签名安装器、按用户安装、随包运行时 | 独立签名/公证 `.app`，通过 DMG 分发 | 仅 Python 源码启动 |
| 启停 | 开始菜单/托盘；开机启动另行选用 | 应用/菜单栏；登录启动另行选用 | 终端启动、Ctrl+C 停止 |
| 升级 | 校验签名、停止采集、迁移配置、失败回滚 | 同左，按 CPU 架构发布 | 关闭服务后替换源码；无自动更新 |
| 卸载 | 卸载器删除程序；选择是否删除配置 | 删除应用；明确提供清理设置选项 | 停止进程后删除独立目录；本版不写用户设置 |
| 发现 | 未来注册到当前用户目录的版本/端口描述，先人工配对再健康检查 | 同左 | 商家端尚未连接；无自动发现 |
| 推理 | 未来主路径调用已授权云服务；自建端可评估 ONNX Runtime CPU/DirectML | 云主路径相同；本机备选可评估 ONNX Runtime CPU/Core ML | 不内置推理运行时或权重 |
| 解码 | 评估 Media Foundation / DirectShow / FFmpeg 构建 | 评估 AVFoundation / VideoToolbox / FFmpeg 构建 | 本版无视频解码 |

平台推理/解码条目是评估候选，不是已验证的兼容性承诺。所有安装、升级、卸载和摄像头权限都必须两平台分别实测；Windows 未验证前不宣布构建成功。

## 6. 云模型选择与许可证

当前没有购买、调用或上传画面，不是用本地模型“模拟云训练”。可继承的是数据协议、标注评测和时间统计；供应商间的训练权重/训练历史不能假定通用。

建议后续做小规模对照评测，再选服务：

1. [百度动态人流量统计](https://ai.baidu.com/ai-doc/BODY/wk3cpyyog)：评测连续进出和人数，不能用单张静态计数替代跨帧跟踪。检查机位、帧率、断流重连后的计数语义与持续调用成本。[计费入口](https://ai.baidu.com/ai-doc/BODY/mk3cpyhfe)。本轮文档抓取超时，因此不把旧免费额度/报价写成当前采购承诺。
2. [千问视觉理解](https://help.aliyun.com/zh/model-studio/vision-model/)：适合评测配置阶段的布局、可见区域和场景建议，再由商户确认。支持视频和 JSON 不等于已经验证了连续客流计数、身份一致性或等待时间准确率。
3. [PaddleDetection PP-Tracking](https://github.com/PaddlePaddle/PaddleDetection/blob/release/2.9/configs/mot/README.md)：后续中国内地自建云推理对照方案。代码、检测权重、跟踪权重、训练数据与打包依赖逐项审查；自建也有 GPU、维护、传输和存储成本。

[阿里云北京地域说明](https://help.aliyun.com/en/model-studio/beijing-access-information)区分接入/存储地域与推理部署范围；当前说明中 Beijing 可采用 China Elastic Zone。**不能仅凭北京入口断言推理始终留在中国内地**；选定具体模型/版本后需核实部署范围、保留政策、训练使用、合同和实际路由。上述网页于 2026-10-20 核对，未来采购仍需复核。

成本应按 `每秒请求数 × 每天运行秒数 × 天数` 先算调用量，再按当时阶梯单价、图片 Token、网关/服务器及流量费用估算。低帧率也可能破坏计数，不能为省钱直接假设每分钟一张与连续跟踪等价。

实际验证记录与命令见 [VALIDATION.md](docs/VALIDATION.md)。当前只有 macOS 实际运行证据；Windows 源码路径已提供，尚未在 Windows 环境运行，更没有 Windows 安装器构建成功证据。

| 阶段 | 交付 | Windows / macOS | 仍需条件 |
| --- | --- | --- | --- |
| v0.2 当前计算试算 | 模拟输入、计算与本机 UI、校准统计、测试与文档 | macOS 运行验证；Windows 未验证 | 无摄像头/云账号；不需要训练 |
| 视频采集与云评测 | 文件/USB/RTSP、预览/画线/区域、供应商适配器、人工标注对照 | 两平台分别验证；当前均未完成 | 合法视频、合适机位、明确上传授权及实际推理地域 |
| 独立安装包 | 下载、安装、启停、升级、卸载、权限诊断 | 各平台签名构建与实机验证 | Windows/macOS 测试机、签名/公证条件 |
| 门店试点与集成 | 另行设计订单、页面聚合、地图、本地发现/配对合同 | 两平台真实安装与弱网评测 | 学校、商户、摄像头管理方授权、用途/标识/个人信息保护核对 |

视觉评测要分别记录进出误计/漏计、队伍人数 MAE、拥挤误判、遮挡、断流重连后重复计数、延迟和费用。时间预测需真实“确认/开工/完成”服务事件和独立留出时段，记录绝对误差、区间覆盖率与区间宽度；本版模拟单元测试不是这些准确率的证据。

不连接真实校园监控。默认不做人脸识别、不跨店追踪、不存可识别长期轨迹。防盗仅为远期研究，不能自动认定或指认某个人偷窃。

可选后续无摄像头模式：商家人工维护交易队伍和服务进度，只提供订单及服务事件能支持的时间段；只填总人数时只显示人数。无需为使用主体商家端强制安装或启用插件。
